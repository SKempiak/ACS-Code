\section{Zero-Queue Baselines}\label{sec:zero-queue}
\rubric{Zero-queue baselines}{25}{Methodologically sound per-level latency measurements with clear units and caveats.}

\begin{hypothesis}
  With a single dependent access in flight, latency should rise in steps at the L1 (\qty{32}{\kibi\byte}),
  L2 (\qty{256}{\kibi\byte}) and L3 (\qty{20}{\mebi\byte}) capacities. We expect roughly 4--5 cycles for
  L1, \ensuremath{\sim}\num{12}~cycles for L2, a few tens of cycles for L3, and \ensuremath{\sim}\qty{80}{\nano\second}
  (hundreds of cycles) for DRAM, matching Skylake-family numbers.
\end{hypothesis}

\begin{knobs}
  Fixed       & one thread pinned to CPU~2; random (Sattolo) pointer chase; one node per \qty{64}{\byte} line \\
  Varied      & working-set size inside each level's plateau window; page size (DRAM only); method (primary vs.\ cross-check) \\
  Script      & \code{Cache_and_Memory_Performance_Profiling/scripts/run.sh zero_queue} \\
\end{knobs}

The ring is a single random cycle over one node per cache line, so each load depends on the previous one
and exactly one request is outstanding---zero-queue latency. Cycles use the in-process effective frequency
(\cref{sec:method}).

\paragraph{Plateau rule.} A level's latency is \emph{not} read at its capacity edge, where the set is
partly spilling (e.g.\ \qty{256}{\kibi\byte} is a transition point, not an L2 point). Instead,
\code{derive.py} takes the median, over all measured sizes $s$ with
$2\,C_{\text{prev}} \le s \le 0.75\,C_{\text{level}}$, of the per-size medians ($C_{\text{prev}} =
\qty{4}{\kibi\byte}$ for L1); DRAM uses every size $\ge 4\times$ the L3. The same values feed the
abstract, introduction and conclusion through generated macros, so they cannot disagree.

\subsection{Analysis}
Latency is flat at \valqty{zq_L1_ns}{\nano\second} (\valnum{zq_L1_cyc}~cycles) while the set fits in L1,
sits at \valqty{zq_L2_ns}{\nano\second} (\valnum{zq_L2_cyc}~cycles) on the L2 plateau (individual sizes
\val{zq_L2_min}--\valqty{zq_L2_max}{\nano\second}; the high end is \qty{192}{\kibi\byte}, where
\qty{4}{\kibi\byte} pages already cause L2 conflict misses, \cref{sec:working-set}), spans
\val{zq_L3_min}--\valqty{zq_L3_max}{\nano\second} across the L3 (median \valqty{zq_L3_ns}{\nano\second};
L3 latency is not a single number because larger sets also miss the second-level TLB and travel further
on the ring), and reaches \valqty{zq_DRAM_ns}{\nano\second} (\valnum{zq_DRAM_cyc}~cycles) in DRAM.
With \qty{2}{\mebi\byte} pages the DRAM figure drops to \valqty{zq_DRAM_hugens}{\nano\second}: the
\valqty{zq_DRAM_walk_ns}{\nano\second} difference is the page walk that every random \qty{4}{\kibi\byte}
access beyond the TLB reach pays (\cref{sec:tlb}), which is why MLC-style tools quote DRAM latency on
huge pages. The cross-check method differs by \val{zq_L1_xdiff}\%, \val{zq_L2_xdiff}\%,
\val{zq_L3_xdiff}\% and \val{zq_DRAM_xdiff}\% on L1, L2, L3 and DRAM. Against the hypothesis, L1 (5
cycles), L2 (\valnum{zq_L2_cyc} vs.\ \ensuremath{\sim}12 cycles) and L3 match; DRAM with \qty{4}{\kibi\byte}
pages is about a third slower than the \ensuremath{\sim}\qty{80}{\nano\second} we expected, and the
\qty{2}{\mebi\byte}-page value shows that most of the excess is the page walk.

Caveats: the L3 and DRAM figures are a single-core view of shared resources on an otherwise idle system;
sequential ``latency'' (\cref{sec:pattern}) is prefetcher throughput, not latency, which is why the
chase is randomized; and both methods are pointer chases, so the cross-check guards against ring
construction and timer errors but not against a shared methodological bias, which only an independent
tool such as MLC could rule out.
