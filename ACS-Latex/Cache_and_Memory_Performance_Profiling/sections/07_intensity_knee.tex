\section{Intensity Sweep and the Throughput--Latency Knee}\label{sec:intensity}
\rubric{Throughput--latency knee}{35}{Clear knee identification, diminishing-returns discussion and a
Little's Law connection.}

\begin{hypothesis}
  A single core cannot saturate the DRAM controller because it can keep only about a dozen demand misses
  in flight (its L1 fill buffers). Adding load should raise delivered bandwidth until the dual-channel
  controller saturates in the low tens of \unit{\gibi\byte\per\second}; past that point extra load should
  buy almost no bandwidth but sharply raise the latency of every request (queueing). By Little's Law,
  saturation needs tens of outstanding lines---more than one core provides.
\end{hypothesis}

\begin{knobs}
  Generators  & \code{mem_loaded}: $T = 0 \ldots 9$ cores (all physical cores except CPU~2), each streaming its own \qty{128}{\mebi\byte} region with \qty{256}{\bit} loads; then $T=9$ throttled by an injection delay of 8--2048 empty iterations per line \\
  Probe       & random pointer chase over \qty{256}{\mebi\byte} on CPU~2, measured in the same window as the generators' throughput \\
  Known MLP   & $T$ cores each running $k$ independent random chases: $T=1$, $k = 1\ldots32$; $T = 2\ldots9$, $k=8$ \\
  Script      & \code{Cache_and_Memory_Performance_Profiling/scripts/run.sh intensity} \\
\end{knobs}

\paragraph{Method.} Each point reports \emph{both} axes from one measurement window: generator threads
publish progress counters, the main thread snapshots them, runs the latency probe for
\qty{200}{\milli\second}, and snapshots again. Throughput is all lines moved (generators plus probe) per
second; latency is the probe's time per dependent access---a demand read issued \emph{under} that load,
i.e.\ MLC's ``loaded latency''. $T=0$ is the unloaded latency of the same setup
($W_0 = \valqty{int_w0_ns}{\nano\second}$).

\paragraph{Knee criterion.} We define the knee objectively as the throughput at which loaded latency
first reaches $2W_0$, walking the thread sweep in order of \emph{offered} load ($T=0,1,\ldots,9$) and
interpolating linearly between the two bracketing points (\code{derive.py}). The same rule applied to the
injection-delay sweep (decreasing delay at $T=9$) is a second estimate, and the point of maximum
throughput/latency is a third. All three come from the CSV, not from the eye.

\subsection{Knee and diminishing returns}
The curve has the textbook shape (\cref{fig:intensity}, \cref{tab:littles-law}). From $T=0$ to
$T=\val{int_sat_threads}$ bandwidth climbs from the probe's own trickle to
\valqty{int_sat_gib}{\gibi\byte\per\second}---already 95\% of the \valqty{int_peak_gib}{\gibi\byte\per\second}
maximum---while latency rises only from \valqty{int_w0_ns}{\nano\second} to \valqty{int_sat_ns}{\nano\second}
(\val{int_sat_ratio}$\times$). Every core added after that buys no bandwidth: delivered bandwidth wanders
between \valqty{int_t7_gib}{\gibi\byte\per\second} and \valqty{int_t8_gib}{\gibi\byte\per\second}
(run-to-run noise; see the IQR in \cref{fig:intensity}), but latency climbs steadily to
\valqty{int_last_ns}{\nano\second} at $T=\val{int_last_threads}$; at the bandwidth maximum it is already
\val{int_peak_ratio}$\times$ the unloaded value. By the $2W_0$ rule the knee lies at
\valqty{int_knee_gib}{\gibi\byte\per\second} (\val{int_knee_frac}\% of peak), between $T=\val{int_knee_prevthreads}$
and $T=\val{int_knee_threads}$. The delay sweep crosses $2W_0$ at \valqty{int_kneed_gib}{\gibi\byte\per\second}
(between delays \val{int_kneed_prevdelay} and \val{int_kneed_delay}), and the throughput/latency maximum is at
$T=\val{int_power_threads}$ (\valqty{int_power_gib}{\gibi\byte\per\second}, \valqty{int_power_ns}{\nano\second}).
The three estimates agree that the useful operating range ends at four to six streaming cores and
\qtyrange{29}{31}{\gibi\byte\per\second}. Beyond it the dual-channel controller, not the cores, is the
bottleneck: requests no longer finish faster, they queue.

\subsection{Little's Law with measured latency}
For every load level we compute the mean number of lines in flight, $L = \lambda W$
\cite{little1961proof}, with $\lambda$ the delivered line rate and $W$ the \emph{measured} loaded latency
of that same window. For comparison, $L_0 = \lambda W_0$ uses the unloaded latency, as the previous version
of this report did. $L_0$ rises to \valnum{int_L0max} lines at saturation and then stays flat: that is the
concurrency the memory system can actually \emph{serve} at about \qty{30}{\gibi\byte\per\second}. $L$, in
contrast, keeps growing to \valnum{int_Lmax} lines at $T=9$; the difference $L - L_0$ is requests waiting in
queues, which is exactly why latency rises without any bandwidth gain. At the knee,
$L=\valnum{int_knee_lines}$.

\paragraph{What the known-concurrency sweep shows.} A first analysis computed $L=\lambda W$ from each
chain's own step time and found $L/N$ between \val{mlp_LN_min} and \val{mlp_LN_max}. That is \emph{not} a
validation of Little's Law: with $W$ defined as the time per chain step, $\lambda W = N$ holds by
construction, so it only confirms the progress accounting. The informative quantity is
$L_{\text{mem}} = \lambda W_{\text{mem}}$, where $W_{\text{mem}}$ is the latency of a memory request measured
at the same time by the probe (\valqty{mlp_t1_wmem}{\nano\second} on average with one generator core). One
core reaches its best random-read bandwidth, \valqty{mlp_t1_peak_gib}{\gibi\byte\per\second}, at
$k=\val{mlp_t1_peak_k}$, and its $L_{\text{mem}}$ never exceeds \valnum{mlp_t1_Lmem_max} lines
(\cref{fig:mlp}). Chains beyond that do not reach memory any sooner: they wait inside the core, so the
per-chain step time grows instead (to \valqty{mlp_t1_last_ns}{\nano\second} at $k=\val{mlp_t1_last_k}$).
About nine outstanding demand misses per core is consistent with the 12 L1D fill buffers of this
Skylake-family core. The single-core curve is not monotonic in $k$ ($k=8$ and $12$ are slower than $k=6$ and
$10$); we did not resolve this generator artifact and use only the envelope. With $k=8$ per core, adding
cores raises bandwidth to \valqty{mlp_peak_gib}{\gibi\byte\per\second} at $T=\val{mlp_peak_T}$
($L_{\text{mem}}=\valnum{mlp_peak_Lmem}$, $W_{\text{mem}}=\valqty{mlp_peak_wmem}{\nano\second}$). Random demand
reads thus reach only about 60\% of the streaming peak: without prefetching, nine cores of this kind keep
about seven lines each in flight and the memory system queues long before it is fully used.

\paragraph{Reconciling one core's streaming concurrency with the fill buffers.} The streaming sweep gives
one core $L=\valnum{int_t1_L}$ lines in flight at \valqty{int_t1_gib}{\gibi\byte\per\second}
(\cref{tab:littles-law}), almost three times the \valnum{mlp_t1_Lmem_max} demand misses one core sustains.
There is no contradiction: in a sequential stream most lines are brought in by the L2 hardware prefetcher,
whose requests are tracked in the L2's own request queue rather than in the L1 fill buffers, so a streaming
core keeps more lines in flight than a core issuing random demand misses. The previous version of this
report claimed ``\ensuremath{\sim}10 fill buffers'' next to a table showing 20 lines for one core and did not
explain the difference; the two measurements now quantify both limits. The \valnum{int_L0max} lines the
controller serves at saturation are about two streaming cores' worth of concurrency (with queueing, four
cores are needed to reach 95\% of peak), but six random-access cores' worth.
