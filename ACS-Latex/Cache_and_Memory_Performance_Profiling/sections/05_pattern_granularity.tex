\section{Access Pattern and Granularity}\label{sec:pattern}
\rubric{Pattern, granularity and read/write sweeps}{35}{Complete, well-controlled bandwidth and latency
comparisons (with \cref{sec:rw-mix}).}

\begin{hypothesis}
  \emph{Access size.} Reading a whole $B$-byte block per access should leave sequential bandwidth roughly
  unchanged but raise random bandwidth steeply with $B$, because a larger block amortises one DRAM latency
  over more lines and lets the prefetchers help. The latency of one dependent $B$-byte access should grow far
  less than $B$, since its lines are fetched in parallel. \emph{Stride.} With one \qty{8}{\byte} element used per stride, useful bandwidth should
  fall roughly as $1/\text{stride}$ once the stride reaches a \qty{64}{\byte} line.
\end{hypothesis}

\begin{knobs}
  Fixed       & 1 thread pinned to CPU~2; \qty{256}{\mebi\byte} DRAM-resident region; 100\% reads; \qty{4}{\kibi\byte} pages \\
  Varied      & pattern (sequential, random); access size $B = 64 \ldots 4096$\,B (primary); byte stride 8--1024 (secondary) \\
  Script      & \code{Cache_and_Memory_Performance_Profiling/scripts/run.sh pattern} \\
\end{knobs}

\paragraph{Definitions.} \emph{Access size} $B$: every byte of a $B$-byte block is read (\qty{256}{\bit}
loads) before the next block, visited in address or shuffled order. For latency, the next block's address
depends on all lines of the current one, so one access is one dependent $B$-byte request. \emph{Stride}
(\cref{fig:stride}): one \qty{8}{\byte} scalar element used per stride.

\subsection{Analysis: access size}
At $B=\qty{64}{\byte}$ sequential blocks stream at \valqty{pat_bw_seq_64}{\gibi\byte\per\second} and
random blocks at \valqty{pat_bw_rand_64}{\gibi\byte\per\second} (\val{pat_bw_ratio_64}$\times$ apart).
Growing the block to \qty{256}{\byte} and \qty{1024}{\byte} lifts random bandwidth to
\valqty{pat_bw_rand_256}{\gibi\byte\per\second} and \valqty{pat_bw_rand_1024}{\gibi\byte\per\second}
(sequential: \valqty{pat_bw_seq_256}{\gibi\byte\per\second}, \valqty{pat_bw_seq_1024}{\gibi\byte\per\second}),
shrinking the gap to \val{pat_bw_ratio_1024}$\times$; at \qty{4096}{\byte} random blocks reach
\valqty{pat_bw_rand_4096}{\gibi\byte\per\second}, close to the sequential \valqty{pat_bw_seq_4096}{\gibi\byte\per\second}.
Contiguous lines within a block overlap their misses and engage the prefetchers; sequential bandwidth is
flat from \qty{256}{\byte} up. Per request, a random dependent \qty{64}{\byte} access costs
\valqty{pat_lat_rand_64_ns}{\nano\second} but a \qty{1024}{\byte} one only
\valqty{pat_lat_rand_1024_ns}{\nano\second}---16 lines for far less than 16 latencies---so one dependent
chain moves \valqty{pat_lat_rand_1024_gib}{\gibi\byte\per\second} instead of
\valqty{pat_lat_rand_64_gib}{\gibi\byte\per\second}. Sequentially chained blocks cost
\valqty{pat_lat_seq_64_ns}{\nano\second} (\qty{64}{\byte}) and \valqty{pat_lat_seq_1024_ns}{\nano\second}
(\qty{1024}{\byte}), the gap to random being latency the prefetcher hides; at \qty{4096}{\byte} it is gone (\valqty{pat_lat_seq_4096_ns}{\nano\second} vs.\ \valqty{pat_lat_rand_4096_ns}{\nano\second}
random): every block starts a new \qty{4}{\kibi\byte} page, and the prefetcher does not cross pages.

\subsection{Analysis: stride, and the line-traffic anomaly}
Sequential useful bandwidth is \valqty{pat_stride_seq_8}{\gibi\byte\per\second} at unit (\qty{8}{\byte})
stride and \valqty{pat_stride_seq_64}{\gibi\byte\per\second} at \qty{64}{\byte}. At \qty{64}{\byte} stride
every access pulls a whole line, so \emph{line} traffic is $8\times$ the useful bandwidth:
\valqty{pat_stride_seq_64_line}{\gibi\byte\per\second}, i.e.\ \val{pat_stride64_over_unit}$\times$ the
unit-stride rate. So the obvious unit-stride scalar read does \emph{not} measure the single-core streaming
limit: with eight loads and adds per line, fewer lines fit in the out-of-order window. Full-line vector reads of large blocks reach
\valqty{pat_bw_seq_max}{\gibi\byte\per\second} (at \qty{64}{\byte} blocks, with loop overhead, only
\val{pat_vec_over_scalar}$\times$ the scalar kernel: \valqty{pat_bw_seq_64}{\gibi\byte\per\second}). The
single-core streaming limit is therefore about \qtyrange{15}{16}{\gibi\byte\per\second}; the loaded-latency
study (\cref{sec:intensity}) uses a two-loads-per-line vector stream.

Contrary to our hypothesis, useful bandwidth does \emph{not} keep falling as
$1/\text{stride}$ beyond one line: it is \valqty{pat_stride_seq_256}{\gibi\byte\per\second} at
\qty{256}{\byte} and \valqty{pat_stride_seq_1024}{\gibi\byte\per\second} at \qty{1024}{\byte}, so touched-line
traffic drops from \valqty{pat_stride_seq_64_line}{\gibi\byte\per\second} to
\valqty{pat_stride_seq_256_line}{\gibi\byte\per\second} and \valqty{pat_stride_seq_1024_line}{\gibi\byte\per\second}.
Each access is then a separate miss, so misses in flight, not bandwidth, limit it. At \qty{64}{\byte} stride DRAM reads are
\valqty{pat_stride_seq_64_imcrd}{\gibi\byte\per\second}, \val{pat_stride_seq_64_imc_over_line}$\times$ the
touched-line traffic. At \qty{256}{\byte} and \qty{1024}{\byte} strides DRAM reads are
\val{pat_stride_seq_256_imc_over_line}$\times$ and \val{pat_stride_seq_1024_imc_over_line}$\times$ the touched
lines (\valqty{pat_stride_seq_256_imcrd}{\gibi\byte\per\second} and
\valqty{pat_stride_seq_1024_imcrd}{\gibi\byte\per\second}): the spatial (adjacent-line) prefetcher fetches the
other half of each \qty{128}{\byte} pair, so every useful \qty{8}{\byte} costs two lines of DRAM traffic.
Random 64\,B blocks show the same pairing (\valqty{pat_bw_rand_64_imcrd}{\gibi\byte\per\second} of DRAM reads
for \valqty{pat_bw_rand_64}{\gibi\byte\per\second} useful). Random strided access is flat at
\val{pat_stride_rand_8}--\valqty{pat_stride_rand_1024}{\gibi\byte\per\second}: every access is an independent
miss.
