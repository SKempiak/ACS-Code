\section{Anomalies and Limitations}\label{sec:anomalies}
\rubric{Report quality}{15}{Readable plots, concise interpretation and thoughtful limitations.}

\subsection{Unexpected results and how they were resolved}
\begin{itemize}
  \item \textbf{Strided ``line traffic'' exceeded the single-core peak.} At \qty{64}{\byte} stride the
        line traffic (\valqty{pat_stride_seq_64_line}{\gibi\byte\per\second}) exceeds the unit-stride
        rate (\valqty{pat_stride_seq_8}{\gibi\byte\per\second}) that the previous version called the
        single-core peak. Hypothesis: the scalar unit-stride kernel is limited by the core's out-of-order
        window, not by DRAM. Test: large full-line vector blocks reach
        \valqty{pat_bw_seq_max}{\gibi\byte\per\second} on the same data, so the real single-core limit is
        \qtyrange{15}{16}{\gibi\byte\per\second} (\cref{sec:pattern}).
  \item \textbf{$L/N=1$ was not a test.} In the known-concurrency sweep, $\lambda$ times the per-chain
        step time equals $N$ by construction. We now report $L_{\text{mem}}$ with the probe's memory
        latency, which saturates at \valnum{mlp_t1_Lmem_max} lines per core (\cref{sec:intensity}).
  \item \textbf{Bandwidth is non-monotonic past saturation.} With 5--9 streaming cores, delivered
        bandwidth scatters between \valqty{int_t7_gib}{\gibi\byte\per\second} and
        \valqty{int_t8_gib}{\gibi\byte\per\second} with wide IQRs, while latency rises steadily. A knee
        rule that sorted points by bandwidth was therefore unstable; it now follows offered load.
  \item \textbf{Single-core chase bandwidth alternates with $k$.} $k=8,12,20$ chains are slower than
        $k=6,10,16$. Probe latency is unchanged, so the cause is in the generator loop, not in memory.
        Unresolved; only the envelope is used.
  \item \textbf{Two unloaded-latency measurements differ by 6\%.} The \code{mem_loaded} probe
        (\valqty{int_w0_ns}{\nano\second}) is faster than \code{mem_latency} at the same
        \qty{256}{\mebi\byte} (\valqty{zq_DRAM256_ns}{\nano\second}). Unresolved; both are reported.
  \item \textbf{A 70/30 read/write mix was 3.4$\times$ slower than pure reads.} Cause: the old kernel
        mixed \qty{8}{\byte} elements, so every line was both read and written. Fixed by mixing at line
        granularity (\cref{sec:rw-mix}); the old numbers are not reused.
  \item \textbf{Huge pages were never granted in the first TLB runs} (\code{AnonHugePages: 0 kB}), so
        those runs (\code{tlb/20261019-232253} and the identical repeat \code{tlb/20261019-233449}) were
        superseded by the verified run in \cref{sec:tlb} and removed, together with every other
        2026-10-19 run.
  \item \textbf{A ``\qty{4}{\kibi\byte}'' baseline can silently use huge pages.} With THP set to
        \sysHugePages{}, a \qty{2}{\mebi\byte}-aligned buffer is backed by huge pages unless the program
        opts out; every \qty{4}{\kibi\byte} buffer now calls \code{MADV_NOHUGEPAGE} and the granted amount
        is recorded, so the page-size label of each curve is verified.
\end{itemize}

\subsection{Limitations}
\begin{itemize}
  \item \textbf{Intel MLC was unavailable.} It is not installed on the test host and could not be
        installed; \code{run.sh mlc} records this in \code{data/raw/mlc/<timestamp>/mlc_status.txt}. The
        cross-checks in \cref{sec:validation} are clearly labelled substitutes: they validate ring
        construction, timing and code path, but share our pointer-chase methodology.
  \item \textbf{Core-only counters.} At \code{perf_event_paranoid}=\sysPerfParanoid{} only user-space
        core events of our own process are available: no uncore/IMC counters (actual DRAM traffic,
        prefetch fills, write-backs) and no kernel-mode events. DRAM traffic for write mixes is therefore
        an estimate (one RFO per written line), and prefetcher traffic is inferred. Generic LLC events map
        to offcore-response events on this core and may undercount prefetch-driven fills. Counters were
        multiplexed when more events were requested than free hardware counters; counts are scaled and
        the running fraction is recorded.
  \item \textbf{Loaded latency is measured with a probe that is itself load.} The probe adds one line in
        flight (included in throughput) and measures a demand read; the streaming generators' prefetches
        may see a different latency, so $L=\lambda W$ for the streaming sweep assumes the probe's latency
        is representative. The known-concurrency chase sweep does not need that assumption.
  \item \textbf{One machine and one memory configuration.} All numbers come from a single i9-10900F on
        one NUMA node; DIMM population and speed could not be read without root. Frequency policy for the
        runs: governor \sysGovernor{}, turbo \sysTurbo{}, SMT \sysSMT{}; cycle figures use the in-process
        effective frequency.
  \item \textbf{Report build backend.} The host has \code{bibtex} but not \code{biber}, so
        \code{biblatex} uses \code{backend=bibtex}.
\end{itemize}
