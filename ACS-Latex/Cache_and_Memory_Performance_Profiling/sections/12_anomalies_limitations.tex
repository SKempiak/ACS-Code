\section{Anomalies and Limitations}\label{sec:anomalies}
\rubric{Report quality}{15}{Readable plots, concise interpretation and thoughtful limitations.}

\subsection{Unexpected results and how they were resolved}
\begin{itemize}
  \item \textbf{An ACPI event storm stole wall time from every core.} In a first complete run (its
        benchmark data were discarded and not retained), the
        in-process add-chain frequency probe read either \qty{2.79}{\giga\hertz} or about
        \qty{2.41}{\giga\hertz} with turbo off, which would have understated DRAM latency by about 14\% in
        cycles. The diagnostic \code{clock_check} run below is retained. Hypothesis: the clock does not change, but the thread loses wall time. Test:
        \code{clock_check} compared core cycles, reference cycles and wall time in \val{cc_acpi_windows}
        windows of \valqty{cc_acpi_window_ms}{\milli\second} on CPUs 2 and 6. The core clock was
        \valqty{cc_acpi_core_ghz}{\giga\hertz} in every window. In \val{cc_acpi_gpe_pct}\% of the windows a
        burst of ACPI general-purpose events occurred (about \val{cc_acpi_gpe_per_window} per window), and in
        those windows the pinned thread executed user code for only \val{cc_acpi_userfrac_gpe} of the wall
        time (quiet windows: \val{cc_acpi_userfrac_quiet}), with no system time or context switches charged
        to it. The probe read \valqty{cc_acpi_probe_gpe}{\giga\hertz} in those windows (quiet:
        \valqty{cc_acpi_probe_quiet}{\giga\hertz}). The lost time is invisible to the OS and hits every core,
        consistent with firmware (SMM) handling of the events. The source, GPE~0x42, was then masked by the
        user, and all data in this report were re-measured. In the final \code{clock_check} run the
        thread keeps \val{cc_userfrac_min}--\val{cc_userfrac} of the wall time, and the probe reads
        \val{probe_st_min}--\valqty{probe_st_max}{\giga\hertz} in every single-thread run (\cref{sec:method}). Cycles are still converted with the fixed
        \qty{2.8}{\giga\hertz} clock, which does not depend on the probe (\cref{sec:method}).
  \item \textbf{The add-chain probe is code-alignment sensitive.} A one-ADD loop ran at one or two cycles per
        iteration depending on where the compiler placed it, so some builds read half the clock. The probe
        now uses a 32-byte-aligned loop of eight dependent ADDs.
  \item \textbf{Unit-stride ``peak'' versus strided line traffic.} At \qty{64}{\byte} stride the line
        traffic (\valqty{pat_stride_seq_64_line}{\gibi\byte\per\second}) exceeds the unit-stride scalar
        read (\valqty{pat_stride_seq_8}{\gibi\byte\per\second}), the kernel one would naturally use as the
        single-core peak. Hypothesis: the scalar kernel is limited by the core's out-of-order window, not by
        DRAM. Test: large full-line vector blocks reach \valqty{pat_bw_seq_max}{\gibi\byte\per\second} on
        the same data, so the single-core limit is \qtyrange{15}{16}{\gibi\byte\per\second}
        (\cref{sec:pattern}).
  \item \textbf{$L/N=1$ is not a test.} In the known-concurrency sweep, $\lambda$ times the per-chain step
        time equals $N$ by construction. The informative quantity is $L_{\text{mem}}$ with the probe's
        memory latency, which saturates at \valnum{mlp_t1_Lmem_max} lines per core (\cref{sec:intensity}).
  \item \textbf{A single-core chase outlier.} With one generator core, $k=12$ chains deliver less bandwidth
        than $k=10$ or $k=16$ at the same memory latency. The probe is unaffected, so the cause is in the
        generator loop, not in memory. Unresolved; only the envelope is used. (In the run disturbed by the
        ACPI storm, $k=8$ and $k=20$ were also low; data not retained, so this cannot be checked from the
        repository.)
  \item \textbf{The two unloaded DRAM latencies agree once the interference is gone.} In the disturbed run
        (data not retained), the \code{mem_loaded} probe and \code{mem_latency} differed by 6\% at
        \qty{256}{\mebi\byte}. In the
        final run they give \valqty{int_w0_ns}{\nano\second} and \valqty{zq_DRAM256_ns}{\nano\second}, consistent with the gap
        having been run-to-run noise from the stolen wall time rather than a property of the two rings.
  \item \textbf{Element-level read/write mixes measure the wrong thing.} Mixing \qty{8}{\byte} elements
        reads every source line and writes every destination line, so a nominal 70/30 mix moves about three
        lines per useful line; mixes must be defined on lines (\cref{sec:rw-mix}).
  \item \textbf{Requested huge pages are not necessarily granted---and vice versa.} An early TLB run (data not
        retained) requested THP and received \code{AnonHugePages: 0 kB}, so its ``huge'' curve was really
        \qty{4}{\kibi\byte} pages. Conversely, with THP set to \sysHugePages{} a
        \qty{2}{\mebi\byte}-aligned ``\qty{4}{\kibi\byte}'' buffer is backed by huge pages unless the program
        opts out. Both page policies are therefore set explicitly before first touch and verified per run
        (\cref{sec:tlb}).
\end{itemize}

\subsection{Limitations}
\begin{itemize}
  \item \textbf{DRAM counters are system-wide.} The memory-controller counts include all traffic in the
        machine; an idle window carries \valqty{cc_imc_rd_idle}{\gibi\byte\per\second} of reads and
        \valqty{cc_imc_wr_idle}{\gibi\byte\per\second} of writes (\code{clock_check}), which is small
        next to every loaded measurement but is not subtracted. Core events are counted in user mode for
        the measuring thread only; generic LLC events map to offcore-response events on this core and may
        undercount prefetch-driven fills. Core counters are multiplexed when more events are requested
        than free hardware counters; counts are scaled and the running fraction is recorded.
  \item \textbf{Single-core traffic model not closed.} With one generator core the memory-controller
        counters read \val{rw_t1_imcest_min}--\val{rw_t1_imcest_max}$\times$ the RFO-counted traffic
        estimate (\cref{sec:rw-mix}); the cause is an untested hypothesis.
  \item \textbf{MLC ran with prefetchers enabled.} Without root, MLC cannot switch the hardware
        prefetchers off, so its latencies use random access (\code{-r}) with prefetchers on, like ours.
  \item \textbf{Loaded latency is measured with a probe that is itself load.} The probe adds one line in
        flight (included in throughput) and measures a demand read; the streaming generators' prefetches
        may see a different latency, so $L=\lambda W$ for the streaming sweep assumes the probe's latency
        is representative. The known-concurrency chase sweep does not need that assumption.
  \item \textbf{One machine and one memory configuration.} All numbers come from a single i9-10900F on one
        NUMA node with two DDR4 channels at \qty{2933}{MT/s} (\cref{sec:intensity}). Frequency policy for the
        runs: governor \sysGovernor{}, turbo \sysTurbo{}, SMT \sysSMT{}.
  \item \textbf{Report build backend.} The host has \code{bibtex} but not \code{biber}, so
        \code{biblatex} uses \code{backend=bibtex}.
\end{itemize}
