\section{Stride and Gather Access}\label{sec:stride}

\begin{hypothesis}
  Unit stride lets each \qty{64}{\byte} cache line serve \num{16} consecutive float32 elements, so
  SIMD helps. As the stride grows, each vector still needs \num{8} elements but they come from
  further apart: once the stride reaches \num{16} elements (\qty{64}{\byte}) every element sits in its
  own cache line and effective bandwidth drops by up to $16\times$. We therefore expect time per
  processed element to rise roughly linearly with stride until it saturates at one cache line per
  element, and we expect the SIMD advantage to vanish for any non-unit stride, because the compiler
  must gather lanes individually. Gather (random permutation) should be the worst case.
\end{hypothesis}

\begin{hypothesis}
  (Added for the extended sweep, before it was run.) The explicit AVX2 gather
  (\code{vgatherdps}, \cref{sec:vectorization}) loads eight lanes per instruction but still needs one
  cache line per element and eight scalar stores, so we expect it to be at best modestly faster than
  the scalar gather in cache and no faster in DRAM. On this CPU the \enquote{Gather Data Sampling}
  microcode mitigation is active (\code{/sys/devices/system/cpu/vulnerabilities/gather_data_sampling}:
  \enquote{Mitigation: Microcode}), which is reported to slow \code{vgatherdps} considerably, so it
  may even lose to the scalar loop.
\end{hypothesis}

\subsection{Analysis}
\Cref{tab:stride} makes the pattern stark. Only unit stride lets \code{native} beat \code{scalar}:
$3.90\times$ at $N=\num{32768}$ and $1.99\times$ in DRAM. At stride~2 and beyond the three builds
agree within \numrange{1.00}{1.02}$\times$ (native vs.\ scalar) at both sizes; \code{autovec} is
within \SI{10}{\percent} of them everywhere, as expected since its strided loop is equally scalar.
Two things happen at once. First, the effective bandwidth collapses. In DRAM the time per processed
element grows from stride~2 to~4 to~8 to~16 as \num{1.14} $\to$ \num{1.83} $\to$ \num{3.42} $\to$
\qty{7.24}{\nano\second} (native), approaching a doubling per step. Once the stride reaches \num{16}
elements, each access pulls a fresh \qty{64}{\byte} line and $15/16$ of every line is wasted. With
$N=\num{32768}$ the span stays in L2/L3 and the progression is milder (\num{0.78} $\to$ \num{1.06}
$\to$ \num{1.85} $\to$ \qty{3.54}{\nano\second}), but the near-doubling from stride~8 to~16 is the
same: the cost per element is set by the cache lines touched, not by arithmetic. Second, the SIMD
advantage disappears. The vectorized body exists only for $s=1$ (GCC's run-time loop versioning,
\cref{sec:vectorization}); every $s>1$ runs the scalar copy of the loop, so no build has vector lanes
to offer. Gather is the worst pattern: \qty{10.1}{\nano\second} per element in DRAM (native),
$29\times$ slower than unit stride, because the random permutation also defeats the hardware
prefetcher. Even at $N=\num{32768}$ it costs \qty{1.92}{\nano\second}, $12\times$ unit stride.

\emph{Hardware gather.} The explicit AVX2 kernel takes \num{3.20} and \qty{10.56}{\nano\second} per
element at $N=\num{32768}$ and \num{4194304}. That is $1.54\times$ and $1.03\times$ the time of the
scalar build's gather, i.e.\ \emph{slower}, decisively so when the data is cache-resident. The
hypothesis written before the run anticipated this. Each 8-lane step issues two \code{vgatherdps},
which the active Gather Data Sampling microcode mitigation is known to make expensive, followed by
eight scalar stores. In DRAM the random line fetches dominate either way and the difference
shrinks to \SI{3}{\percent}. We could not run without the mitigation (that needs a reboot with
root), so the attribution remains a hypothesis (\cref{sec:anomalies}). Either way, a SIMD gather
does not recover the unit-stride advantage. The practical lesson is that access pattern, not vector
width, is the first-order knob for these kernels.
