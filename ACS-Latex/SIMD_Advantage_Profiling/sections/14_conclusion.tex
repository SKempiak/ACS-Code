\section{Conclusion}\label{sec:conclusion}

On this AVX2 machine SIMD pays off handsomely only when two conditions hold at once: the data fits in
cache and the kernel is not a serial reduction. Under those conditions \code{-march=native} gives
SAXPY, elementwise multiply and the stencil roughly $3.5$--$5.8\times$ over scalar at
$N=\num{4096}$ (the generic SSE build gets $2.6$--$3.0\times$), below the $8\times$ lane count
because load/store issue, not the FMA units, limits the vector loop. Once the working set spills to
DRAM the vector builds run \emph{at} the independently measured bandwidth roof, and the advantage
compresses to $1.7$--$1.9\times$ for SAXPY, $1.4$--$1.5\times$ for multiply and $2.7$--$2.8\times$ for the
stencil. What remains is not extra SIMD throughput but
the scalar loops' own instruction cost, which at the fixed \qty{2.8}{\giga\hertz} clock still
exceeds the memory time; it would shrink further at a higher clock. Data type scales the
cache-resident gain through lane count (float64 halves it), and access pattern dominates everything
else: any non-unit stride or a gather erases the SIMD benefit outright, and AVX2's hardware gather is
even slower than the scalar loop on this mitigated CPU. The single most important lesson for writing
and benchmarking vectorized code is that ``the loop vectorized'' is not ``the loop is fast''. Our
memory-bound SAXPY gains nothing from more lanes, and our non-reassociated dot product, though it
compiles to genuine SIMD, runs at exactly the \num{0.5}~FLOP/cycle its dependency chain allows. Only
a controlled sweep across working-set size, plus disassembly, hardware counters and a measured
roofline, reveals why.
