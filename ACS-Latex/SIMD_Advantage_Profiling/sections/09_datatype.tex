\section{Data Type Comparison}\label{sec:dtype}

\begin{hypothesis}
  A \qty{256}{bit} register holds \num{8} float32 but only \num{4} float64 lanes, so float64 should
  show roughly half the SIMD speedup of float32 for the same kernel while data is cache-resident.
  int32 elementwise multiply should behave like float32 (\num{8} lanes, one \code{vpmulld}). In DRAM,
  float64 moves twice the bytes per element, so its \emph{absolute} throughput should be lower and
  its speedup should compress toward $1\times$ just as float32 does.
\end{hypothesis}

\subsection{Analysis}
The lane-count prediction holds closely for the cache-resident multiply. At $N=\num{1024}$ the native
speedups are float32 $5.24\times$, int32 $5.34\times$, and float64 $2.83\times$---float64 is
$0.54\times$ of float32, within a few percent of the expected $1/2$ from halving the lanes. The
float32/int32 pairing confirms the effect is lane count and not a floating-point quirk: int32 uses
\code{vpmulld} over \num{8} lanes and lands right on the float32 curve. The ratio holds mid-cache too
($N=\num{16384}$: f32 $3.09\times$ vs f64 $1.45\times$; $N=\num{65536}$: $1.97\times$ vs
$1.29\times$).

In DRAM the picture changes as predicted: at $N=\num{16777216}$ every speedup has compressed (f32
$1.22\times$, f64 $1.10\times$), and float64's \emph{absolute} throughput is about half of float32's
(\num{1.0} vs \qty{2.0}{\giga\flop\per\second}) because each element moves \qty{8}{\byte} instead of
\num{4} and the kernel is bandwidth-bound. So data type acts through two separate mechanisms: lane
count sets the cache-resident speedup ceiling, while bytes-per-element sets the DRAM throughput. A
kernel that looks ``half as fast in float64'' in cache is really just running \num{4} lanes instead
of \num{8}; the same kernel in DRAM is half as fast for the different reason that it has twice the
traffic.
