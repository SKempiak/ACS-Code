\section{Data Type Comparison}\label{sec:dtype}

\begin{hypothesis}
  A \qty{256}{bit} register holds \num{8} float32 but only \num{4} float64 lanes, so float64 should
  show roughly half the SIMD speedup of float32 for the same kernel while data is cache-resident.
  int32 elementwise multiply should behave like float32 (\num{8} lanes, one \code{vpmulld}). In DRAM,
  float64 moves twice the bytes per element, so its \emph{absolute} throughput should be lower and
  its speedup should compress toward $1\times$ just as float32 does.
\end{hypothesis}

\subsection{Analysis}
The lane-count prediction holds for most cache-resident points (\cref{tab:dtype}). At
$N=\num{1024}$ the native float64 speedup is \numrange{0.52}{0.59} of float32's for all three
kernels (multiply $2.82\times$ vs $5.19\times$, SAXPY $3.28\times$ vs $5.60\times$, stencil
$1.73\times$ vs $3.35\times$), close to the expected $1/2$. The int32 multiply, which \code{native}
compiles to one \code{vpmulld} over \num{8} lanes, lands on the float32 curve ($5.37\times$). The
ratio is not universal, however. At $N=\num{16384}$ the stencil keeps $3.02\times$ in float64 against
$3.44\times$ in float32 (\num{0.88}): the float32 stencil is depressed at exactly these sizes by the
slow cache-resident regime of \cref{sec:anomalies}, while float64 runs at
\qty{13.2}{\giga\flop\per\second}. And by $N=\num{65536}$, where multiply is L2/L3-bound, its ratio
narrows to $1.40\times$ vs $2.11\times$.

\emph{Operation cost.} Lane count is not the only factor. \code{autovec} gains $3.53\times$ on
float32 multiply at $N=\num{1024}$ (one \code{mulps} per \num{4} lanes) but only $1.86\times$ on
int32: SSE2 has no packed 32-bit multiply (\code{pmulld} is SSE4.1), so the disassembly emulates it
with two \code{pmuludq}, two shifts, two \code{pshufd} and a \code{punpckldq}---seven
instructions per \num{4} lanes.

In DRAM every speedup compresses as predicted ($N=\num{16777216}$, native: float32 $1.60$--$2.79\times$,
float64 $1.17$--$1.68\times$), and float64 now keeps \SIrange{60}{73}{\percent} of the float32 gain
rather than half. The separate baseline sweep measured $1.51\times$ for float32 multiply at the
same $N$ (\cref{sec:baseline}); the difference is mostly the native side (\num{1.72} here vs
\qty{1.63}{\giga\flop\per\second}), a \SI{6}{\percent} run-to-run spread of DRAM-bound throughput,
so we quote multiply's DRAM speedup as $1.5\text{--}1.6\times$. Float64's \emph{absolute}
multiply throughput is under half of float32's (\num{0.80} vs \qty{1.72}{\giga\flop\per\second})
because each element moves \qty{8}{\byte} instead of \num{4}. So data type acts through three
mechanisms: lane count and the cost of the vector operation set the cache-resident speedup, while
bytes per element set the DRAM throughput.
