\section{Vectorization Verification}\label{sec:vectorization}
\rubric{Vectorization verification}{15}{Clear evidence that SIMD instructions are used, with a correct
reading of vector width, FMA and masking.}

\begin{hypothesis}
  The \code{scalar} build should emit only scalar SSE (\code{ss}/\code{sd}) instructions and report
  zero vectorized loops. \code{autovec}, limited to the generic SSE2 target, should vectorize the
  streaming kernels at \qty{128}{bit} (\num{4} float32 lanes). \code{native} should vectorize them at
  \qty{256}{bit} (\code{ymm}, \num{8} float32 / \num{4} float64 lanes) and fuse the multiply--add in
  SAXPY and the stencil into \code{vfmadd}. We expect the compiler to \emph{refuse} to vectorize the
  dot-product reduction usefully, because summation reassociation is illegal without
  \code{-ffast-math}.
\end{hypothesis}

\Cref{tab:vec-summary} counts, for each kernel function and variant, the instructions that operate on
vector registers or use packed operations, extracted by \code{objdump} in \code{make report}. (A few
``SIMD'' matches in the scalar column are register-clearing \code{pxor}/\code{movaps} on \code{xmm},
not vectorized loop bodies---the compiler reports \emph{zero} vectorized loops for \code{scalar}.)

\subsection{Compiler report}
The evidence below (\code{data/raw/vectorization/20261021-001032}) comes from \code{make report},
which recompiles \code{src/kernels.c} with each variant's exact flags and the same GCC as the timed
builds. \code{kernels.c} has not changed since. We checked with \code{objdump} that every kernel
function there has the same instruction sequence as in the linked \code{simd_bench} binaries that
produced the measurements, differing only in absolute addresses and alignment padding.
\code{make report} does not record an \code{env.txt}; the environment is that of the timed runs
(\cref{tab:environment}).

GCC's \code{-fopt-info-vec} confirms the widths. For SAXPY (\code{kernels.c:29}):
\begin{lstlisting}[style=excerpt]
# native  (-O3 -march=native):
src/kernels.c:29:26: optimized: loop vectorized using 32 byte vectors and unroll factor 8
src/kernels.c:29:26: optimized: epilogue loop vectorized using 16 byte vectors and unroll factor 4
# autovec (-O3, generic x86-64):
src/kernels.c:29:26: optimized: loop vectorized using 16 byte vectors and unroll factor 4
# scalar  (-O3 -fno-tree-vectorize): 0 loops vectorized
\end{lstlisting}
\qty{32}{\byte} vectors $=$ \qty{256}{bit} $=$ \num{8} float32 lanes (native); \qty{16}{\byte} $=$
\qty{128}{bit} $=$ \num{4} lanes (autovec). GCC's ``unroll factor'' is the vectorization factor
(elements per iteration), not extra unrolling: the disassembly below has one \code{ymm} FMA per
iteration. The \qty{128}{bit} epilogue handles a remainder of \num{4} or more, and up to three
leftover elements run as scalar iterations. The loop is \emph{versioned} for possible aliasing
between \code{x} and \code{y} (a run-time overlap check), and GCC does not peel iterations to reach
an aligned start.

\subsection{Disassembly}
The native SAXPY inner loop is a single fused multiply--add on \code{ymm} registers:
\begin{lstlisting}[style=excerpt]
vmovups   (%rdi,%rax,1),%ymm0           # load 8 x[i]
vfmadd213ps (%rsi,%rax,1),%ymm1,%ymm0   # ymm0 = a*x + y   (one FMA, 8 lanes)
vmovups   %ymm0,(%rsi,%rax,1)           # store 8 y[i]
\end{lstlisting}
whereas the scalar build does one element at a time with scalar SSE. It cannot fuse the
multiply and add because the generic \code{x86-64} target it compiles for does not include the FMA
instruction set (GCC's default \code{-ffp-contract=fast} would contract them if FMA were available,
as it does in \code{native}):
\begin{lstlisting}[style=excerpt]
movss (%rdi,%rax,4),%xmm0  # x[i]
mulss %xmm1,%xmm0          # a*x[i]
addss (%rsi,%rax,4),%xmm0  # + y[i]   (separate mul + add: generic x86-64 has no FMA)
movss %xmm0,(%rsi,%rax,4)  # y[i]
\end{lstlisting}

The dot product is the instructive exception. Native \emph{does} multiply eight lanes at once, but
the horizontal sum is a serial chain of scalar \code{vaddss}:
\begin{lstlisting}[style=excerpt]
vmulps (%rdi,%rax,1),%ymm1,%ymm1  # 8 products at once ...
vaddss %xmm1,%xmm0,%xmm0          # ... but summed one lane at a time,
vaddss %xmm3,%xmm0,%xmm0          #     in strict source order
...
\end{lstlisting}

\subsection{Stride and gather code}
\Cref{tab:vec-summary} credits \code{saxpy_f32_stride} with \code{ymm} instructions in
\code{native}, but that is loop \emph{versioning}, not strided SIMD: GCC tests \code{s == 1} at run
time and only that copy of the loop is vectorized (the same \code{vmovups}/\code{vfmadd213ps} body as
SAXPY). For $s>1$ the code is a scalar \code{vfmadd213ss} loop in \code{native} and
\code{mulss}/\code{addss} in the other builds. The plain gather loop (\code{saxpy_f32_gather}) is not
vectorized by any build (\enquote{no vectype for stmt}), so we added an explicit AVX2 version,
\code{saxpy_f32_gather_avx2}, compiled only into \code{native}:
\begin{lstlisting}[style=excerpt]
vmovdqu    (%rax),%ymm1                 # 8 indices idx[i..i+7]
vgatherdps %ymm5,(%rdi,%ymm1,4),%ymm0   # gather 8 x[idx]
vgatherdps %ymm7,(%rsi,%ymm1,4),%ymm3   # gather 8 y[idx]
vfmadd132ps %ymm4,%ymm3,%ymm0           # one 8-lane FMA
vmovss     %xmm0,(%rsi,%rdx,4)          # ... then 8 scalar stores:
vextractps $0x1,%xmm0,(%rsi,%rdx,4)     #     AVX2 has no scatter
\end{lstlisting}
It is what a hand-vectorized gather looks like on this ISA: the loads are SIMD, the stores cannot be.

\subsection{Interpretation}
The evidence matches the hypothesis. \code{native} uses \code{ymm} (\qty{256}{bit}) with FMA for
SAXPY, multiply, and the stencil; \code{autovec} uses \code{xmm} (\qty{128}{bit}); \code{scalar} is
genuinely scalar. Tails are handled by a narrower vectorized epilogue (a \qty{128}{bit} loop), not a
scalar remainder---there are no AVX-512 mask registers here because the CPU has no AVX-512. The dot
product shows why ``the loop vectorized'' is not the same as ``the loop is fast'': without
\code{-ffast-math} the compiler keeps the reduction's addition order, so the packed multiplies feed a
latency-bound scalar accumulator. We quantify the throughput consequence in
\cref{sec:baseline,sec:negative}.
