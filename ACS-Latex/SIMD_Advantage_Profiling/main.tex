\begin{abstract}
  We quantify scalar-versus-SIMD speedup for four single-threaded numeric kernels (SAXPY, dot
  product, elementwise multiply and a 3-point stencil) on an Intel Core i9-10900F (Comet Lake,
  AVX2+FMA, \qty{256}{bit} vectors) running at a fixed \qty{2.8}{\giga\hertz}. With cache-resident
  data a \code{-march=native} build reaches about $5.8\times$ over scalar for SAXPY (\num{8} float32
  lanes), while the generic auto-vectorized (SSE, \qty{128}{bit}) build reaches about $3\times$; the
  gain compresses to $\approx1.7\text{--}1.9\times$ once the working set spills to DRAM. There the
  native kernels sit \emph{on} the measured DRAM bandwidth roof, and the speedup that remains only
  reflects that scalar SAXPY, which hardware counters show needs $\approx1.8$ cycles of core work per
  element, cannot keep up with memory at this clock. Float64 roughly halves the SIMD advantage
  (\num{4} lanes), and non-unit stride or gather access erases it entirely; an explicit AVX2
  hardware gather (\code{vgatherdps}) is even $1.5\times$ \emph{slower} than the scalar gather in
  cache. Our negative case is memory-bound SAXPY: the loop provably vectorizes, yet wider vectors buy
  nothing in DRAM because it already runs at the bandwidth roof; a second anomaly is the dot product,
  whose non-reassociated reduction leaves a \num{4}-cycle scalar dependency chain and
  $\approx1\times$ speedup despite packed multiplies. A cache-aware roofline whose ceilings are
  measured by separate microbenchmarks---an FMA-throughput loop
  (\qty{89.1}{\giga\flop\per\second} float32, \num{32.0}~FLOP/cycle) and a STREAM-style triad per
  cache level (from \qty{207}{\gibi\byte\per\second} in L1 down to \qty{24.3}{\gibi\byte\per\second} from DRAM)---places every
  L3- and DRAM-resident native streaming kernel within \SI{11}{\percent} of its bandwidth roof.
\end{abstract}
