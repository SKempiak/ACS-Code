\section{Anomalies and Limitations}\label{sec:anomalies}
\rubric{Report quality}{15}{Clear figures, concise explanation and thoughtful limitations.}

\subsection{Unexpected results}
\begin{itemize}
  \item \textbf{Random writes beat random reads at low queue depth.} At QD=1, \qty{4}{\kibi\byte} writes
        hit \qty{68}{k} IOPS (\qty{14.7}{\micro\second}) versus reads at \qty{20}{k}
        (\qty{49.6}{\micro\second}), and at QD=16 pure writes (\qty{186}{k} IOPS) beat pure reads
        (\qty{105}{k}). Hypothesis: the controller acknowledges writes from its SLC/DRAM buffer before the
        flash program completes, whereas a read must wait for the NAND sense. Consistent with the write
        buffer also explaining why \emph{mixed} workloads are slower than either pure case
        (\cref{sec:rw-mix}).
  \item \textbf{Sequential QD=1 read throughput is modest (\qty{227}{\mebi\byte\per\second}).} Lower than
        the drive's headline rating. Hypothesis: with one outstanding \qty{128}{\kibi\byte} request and
        \code{O_DIRECT} (no OS read-ahead), the device is under-fed; the block-size and queue-depth sweeps
        show throughput rising to \qty{1.5}{\gibi\byte\per\second} with larger blocks and
        \qty{620}{\mebi\byte\per\second} of random \qty{4}{\kibi\byte} at QD=128, so this is a
        single-request artifact, not a device ceiling.
  \item \textbf{Sustained-write throughput dips then recovers} rather than falling off an SLC cliff
        (\cref{fig:device-state}). Hypothesis: the \qty{2}{\gibi\byte} footprint is too small and the run
        too short to exhaust the SLC cache; the dip is the initial flush transient. Tested only
        indirectly---a full-capacity run would be needed to see the true steady-state QLC rate.
\end{itemize}

\subsection{Limitations}
\begin{itemize}
  \item \textbf{FIO not available.} \sysFio{}; measurements use \code{blkbench}, an O\_DIRECT
        \code{libaio} stand-in. FIO-only conveniences---full latency histograms beyond p99.9,
        \code{numjobs} scaling, built-in SMART logging and its exact ioengine knobs---are approximated or
        omitted, not faked.
  \item \textbf{No \code{iostat}/\code{perf} cross-check.} Effective queue depth is verified in-band via
        Little's Law (\cref{tab:littles-law}) rather than against \code{iostat} aqu-sz.
  \item \textbf{SMART/thermal need root.} Temperature, data-units-written and media-error counters are
        unavailable (\code{smartctl}/\code{nvme} require privileges we lack), so thermal/throttling and
        wear claims are limited to what the throughput trace shows.
  \item \textbf{Filesystem, not raw device; small LBA range.} I/O goes to a \qty{2}{\gibi\byte} disposable
        file on an ext4 filesystem (the data-safety requirement), not a raw partition, so ext4 extent
        mapping adds a thin layer and only \num{0.4}\% of the \qty{512}{\giga\byte} LBA space is exercised.
        Full-span and true steady-state behaviour are out of scope.
  \item \textbf{Fixed data pattern; short runs.} Writes use a constant \code{0xA5} fill (compressibility
        not varied) and runs are \qtyrange{4}{6}{\second}; the SLC-cache size and long-term steady state
        were not measured. One drive, one firmware.
  \item \textbf{Report build backend.} Builds cleanly with \code{make ssd} and \code{make final}; the host
        has \code{bibtex} but not \code{biber}, so \code{biblatex} uses \code{backend=bibtex}. The only
        artifact is a benign \enquote{Please (re)run BibTeX} notice---no unresolved \code{[?]} markers.
\end{itemize}
