\section{Zero-Queue Baselines}\label{sec:zero-queue}

\begin{hypothesis}
  At QD=1 a single I/O is in flight, so latency is the full host-stack + controller + flash path. We
  expect \qty{4}{\kibi\byte} random reads in the tens of microseconds (flash read dominates) and
  \qty{128}{\kibi\byte} sequential transfers to be bandwidth-limited at a few hundred
  \unit{\micro\second}. Writes should be \emph{faster} than reads at QD=1 because the SSD's DRAM/SLC
  write buffer acknowledges them before the flash program completes.
\end{hypothesis}

\begin{knobs}
  Fixed       & iodepth 1; one job; \code{O_DIRECT}; 5 repetitions of \qty{4}{\second} (write points also
                stop at \qty{256}{\mebi\byte}) \\
  Cases       & 4~KiB random read, 4~KiB random write, 128~KiB sequential read, 128~KiB sequential write \\
  Order       & random read $\to$ random write $\to$ sequential re-fill of the file $\to$ sequential read
                $\to$ sequential write (the re-fill keeps the sequential read independent of the random
                writes; \cref{sec:layout}) \\
  Script      & \code{SSD_Performance_Profiling/scripts/run.sh zero_queue} \\
\end{knobs}

\subsection{Analysis}
The QD=1 numbers identify an NVMe SSD, not a rotational disk. \qty{4}{\kibi\byte} random read latency is
\csvq[1]{zero_queue}{mode=read,pattern=rand}{lat_mean_us_median}\,\si{\micro\second}, not the
milliseconds an HDD would show, and it is dominated by the NAND read plus the NVMe/\code{libaio} host
path, with no seek. Random \emph{writes} take only
\csvq[1]{zero_queue}{mode=write,pattern=rand}{lat_mean_us_median}\,\si{\micro\second}
(\csvq{zero_queue}{mode=write,pattern=rand}{iops_median} IOPS), because the controller acknowledges them
from its write buffer (SLC cache plus controller SRAM) before the flash program finishes. A QD=1 read
has no such buffer to hide behind.

The \qty{128}{\kibi\byte} sequential rows are limited by per-request latency. The read takes
\csvq[0]{zero_queue}{mode=read,pattern=seq}{lat_mean_us_median}\,\si{\micro\second} per request
(\csvq{zero_queue}{mode=read,pattern=seq}{mibps_median}\,MiB/s), and the single outstanding request
leaves the device idle between transfers. \Cref{sec:block-size,sec:queue-depth} show throughput climbing
once larger blocks or deeper queues keep more data moving.

Two caveats apply. First, a QD=1 random read cannot be prefetched, so this is a genuine floor. Second,
the p99.9 column already shows occasional outliers of several hundred microseconds to milliseconds from
background flush and garbage collection, which preview the tail behaviour in \cref{sec:tail}.

An early pilot run, since discarded, measured this sequential read directly after the random-write
case and got only a fraction of the rate above. That discrepancy led to the re-fill step in the
procedure, and the \code{layout} experiment (\cref{sec:layout}) reproduces it:
\csvq{layout}{experiment=layout_rand_overwritten,bs=131072,qd=1}{mibps_median} vs.\
\csvq{layout}{experiment=layout_seq_filled,bs=131072,qd=1}{mibps_median}\,MiB/s.
