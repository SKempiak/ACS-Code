\section{Zero-Queue Baselines}\label{sec:zero-queue}

\begin{hypothesis}
  At QD=1 a single I/O is in flight, so latency is the full host-stack + controller + flash path. We
  expect \qty{4}{\kibi\byte} random reads in the tens of microseconds (flash read dominates) and
  \qty{128}{\kibi\byte} sequential transfers to be bandwidth-limited at a few hundred
  \unit{\micro\second}. Writes should be \emph{faster} than reads at QD=1 because the SSD's DRAM/SLC
  write buffer acknowledges them before the flash program completes.
\end{hypothesis}

\begin{knobs}
  Fixed       & iodepth 1; one job; \code{O_DIRECT}; 5 repetitions of \qty{4}{\second} (write points also
                stop at \qty{256}{\mebi\byte}) \\
  Cases       & 4~KiB random read, 4~KiB random write, 128~KiB sequential read, 128~KiB sequential write \\
  Order       & random read $\to$ random write $\to$ sequential re-fill of the file $\to$ sequential read
                $\to$ sequential write (the re-fill keeps the sequential read independent of the random
                writes; \cref{sec:layout}) \\
  Script      & \code{SSD_Performance_Profiling/scripts/run.sh zero_queue} \\
\end{knobs}

\subsection{Analysis}
The QD=1 numbers identify an NVMe SSD, not a rotational disk: \qty{4}{\kibi\byte} random reads take
\csvq[1]{zero_queue}{mode=read,pattern=rand}{lat_mean_us_median}\,\si{\micro\second}, dominated by the
NAND read plus the NVMe/\code{libaio} host path, with no seek. Random \emph{writes} take only
\csvq[1]{zero_queue}{mode=write,pattern=rand}{lat_mean_us_median}\,\si{\micro\second}
(\csvq{zero_queue}{mode=write,pattern=rand}{iops_median} IOPS), because the controller acknowledges them
from its write buffer (SLC cache plus SRAM) before the flash program finishes; a read has no such buffer.
The \qty{128}{\kibi\byte} sequential
read takes \csvq[0]{zero_queue}{mode=read,pattern=seq}{lat_mean_us_median}\,\si{\micro\second} per
request (\csvq{zero_queue}{mode=read,pattern=seq}{mibps_median}\,MiB/s): one outstanding request leaves
the device idle between transfers, which \cref{sec:block-size,sec:queue-depth} remove. The p99.9 column
already shows background flush and GC outliers (\cref{sec:tail}).

\textbf{The sequential-write row is unstable} (IOPS IQR
\csvq{zero_queue}{mode=write,pattern=seq}{iops_q25}--\csvq{zero_queue}{mode=write,pattern=seq}{iops_q75}).
Its first two repetitions ran at \num{490} and \num{891} IOPS with p99 of \qtyrange{30}{35}{\milli\second},
the last three at \numrange{5100}{5460} IOPS, with p50 near \qty{90}{\micro\second} throughout. It
directly followed the \qty{2}{\gibi\byte} sequential re-fill, so we read the slow repetitions as the
controller flushing that burst; the median describes the recovered state, not a stable baseline. The
re-fill itself exists because a discarded pilot that read sequentially right after the random writes got
only a fraction of this rate (\cref{sec:layout}).
