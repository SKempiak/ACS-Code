\section{Queue-Depth Sweep}\label{sec:queue-depth}

\begin{hypothesis}
  IOPS should rise steeply with queue depth as the SSD's parallel NAND channels fill, then saturate at a
  knee beyond which latency grows roughly linearly with queue depth for no extra throughput. By Little's
  Law the number of outstanding I/Os $L=\lambda W$ should track the configured iodepth while the queue
  stays full; where it stops tracking reveals a host-side or engine limit.
\end{hypothesis}

\subsection{Knee}
We define the knee as \emph{the smallest QD whose doubling raises median IOPS by less than
\qty{10}{\percent}}. Past that point, most of any extra concurrency becomes added latency rather than
throughput.

\textbf{Reads.} The rule gives QD~\csvq{queue_depth_knee}{mode=read}{knee_qd}
(\csvq{queue_depth_knee}{mode=read}{knee_iops} IOPS,
\csvq[0]{queue_depth_knee}{mode=read}{knee_lat_us}\,\si{\micro\second} mean). Doubling to
QD~\csvq{queue_depth_knee}{mode=read}{next_qd} adds only
\csvq[1]{queue_depth_knee}{mode=read}{gain_pct}\,\% IOPS. The preceding doubling, QD 32$\to$64, still
gained \qty{15}{\percent}. The grid doubles at each step, so the knee lies between 32 and 64.

\textbf{Writes.} Applied literally, the rule returns QD~\csvq{queue_depth_knee}{mode=write}{knee_qd}.
That is an artifact. The QD=8 write point caught a buffer-flush stall: median
\csvq{queue_depth}{qd=8,mode=write}{iops_median} IOPS with an IQR of
\csvq{queue_depth}{qd=8,mode=write}{iops_q25}--\csvq{queue_depth}{qd=8,mode=write}{iops_q75} and a p99
of \csvq[1]{queue_depth}{qd=8,mode=write}{lat_p99_us_median}\,\si{\micro\second}. The rule therefore saw
a fall rather than a gain. Read with that point excluded, write IOPS rise from
\csvq{queue_depth}{qd=1,mode=write}{iops_median} (QD=1) to
\csvq{queue_depth}{qd=4,mode=write}{iops_median} (QD=4) and
\csvq{queue_depth}{qd=16,mode=write}{iops_median} (QD=16), then stay at
\csvq{queue_depth}{qd=32,mode=write}{iops_median}--\csvq{queue_depth}{qd=256,mode=write}{iops_median}
out to QD=256. The write knee is effectively QD\,$\approx$\,16. The write plateau of
\ensuremath{\sim}\num{250}k IOPS $\times$ \qty{4}{\kibi\byte} $\approx$ \qty{0.97}{\gibi\byte\per\second}
matches the SLC ingest rate measured in \cref{sec:block-size}. Writes saturate the buffer's intake, not
the NAND parallelism that limits reads.

\subsection{Little's Law as a consistency check}
Little's Law \cite{little1961proof} relates the mean number of requests in a system $L$, the throughput
$\lambda$ and the mean time in system $W$: $L=\lambda W$. In a \emph{closed-loop} harness it holds
\emph{by construction}. There are exactly QD request slots, and each completion is resubmitted
immediately, so $\lambda W = \text{QD}\cdot W/(W+g)$, where $g$ is the host-side gap between reaping a
completion and resubmitting it. Matching QD therefore does not show that the device behaves in a
particular way. It shows that the timers are consistent, that no slot is lost, and that the host keeps
up ($g\ll W$). A ratio $L/\text{QD}$ clearly below 1 would mean the issuing thread, not the device, is
the bottleneck. On a tmpfs control, where I/O completes synchronously inside \code{io_submit},
\code{make test} measures $L/\text{QD}\approx0.57$ at QD=8. Note also that $W$ is measured from
submission, so $L$ counts requests in the kernel block layer and driver as well as in the device; the
true device-queue occupancy can only be lower.

\subsection{Analysis}
Read IOPS climb from \csvq{queue_depth}{qd=1,mode=read}{iops_median} at QD=1 to
\csvq{queue_depth}{qd=16,mode=read}{iops_median} at QD=16 and
\csvq{queue_depth}{qd=32,mode=read}{iops_median} at QD=32, then flatten at
\csvq{queue_depth}{qd=64,mode=read}{iops_median}--\csvq{queue_depth}{qd=256,mode=read}{iops_median}.
Scaling is sub-linear from the start. Successive doublings from QD=1 add 56, 39, 60, 47, 34, 15, 4.5 and
1.8\,\%, with no distinct regime of linear scaling. The pilot run's impression that QD 1$\to$4 scaled
unusually poorly did not reproduce: here it scaled $2.2\times$. Beyond the knee, mean latency doubles
with each doubling of QD
(\csvq[0]{queue_depth}{qd=64,mode=read}{lat_mean_us_median}$\to$%
\csvq[0]{queue_depth}{qd=128,mode=read}{lat_mean_us_median}$\to$%
\csvq[0]{queue_depth}{qd=256,mode=read}{lat_mean_us_median}\,\si{\micro\second}), which is the textbook
saturation signature. With $\lambda$ flat, $L=\lambda W$ can follow QD only if $W$ grows in proportion,
so every added request simply waits.

For reads, $L/\text{QD}$ stays between 0.987 and 0.998 at every depth up to 256
(\cref{tab:littles-law}). The single \code{libaio} thread keeps the queue full, and the saturation
belongs to the device. For writes the ratio is 0.95--0.997. The lowest value, 0.95 at QD=128, coincides
with the widest p99.9 there
(\csvq[0]{queue_depth}{qd=128,mode=write}{lat_p999_us_median}\,\si{\micro\second}). We read it as
completions bunching around a flush stall rather than a host limit, but with five repetitions we cannot
separate the two.

The practical reading for reads: QD\,$\approx$\,32--64 extracts nearly all the throughput at a quarter
to half a millisecond, and deeper queues only buy latency. Writes need only QD\,$\approx$\,16, as long as
the SLC cache has room. Once it does not, write throughput is set by QLC programming, whatever the queue
depth (\cref{sec:device-state}).
